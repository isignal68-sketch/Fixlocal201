Latest fix (this build): the actual Next.js build now succeeds completely
end to end — compiles, lints, type-checks, generates all 81 static pages,
and reaches "Build Completed" / "Deploying outputs...". The deployment was
still failing because next@15.0.3 has a critical (CVSS 10.0) remote code
execution vulnerability, CVE-2025-66478, affecting the React Server
Components protocol in Next.js 15.x versions below 15.4.8. Vercel's
platform-level security policy blocks deploys of versions affected by
certain critical CVEs, which is very likely why the log showed "Vulnerable
version of Next.js detected, please update immediately" as the last line
before failure. Upgraded next and eslint-config-next from 15.0.3 to
15.0.5 — the minimal patched release in the same 15.0.x line, chosen to
keep this change as small as possible rather than jumping to a later
minor version. This does not change React (still 18.3.1) or any other
dependency, and Next 15.0.5's peer dependency requirements are identical
to 15.0.3's.

Quick way to confirm you have THIS exact version: open
src/components/ui/button.tsx and look for "slotProps" near the middle of
the file. If it's there, you have the current build.

Latest fix (this build): v11's fix for the React.Children.only crash
re-introduced `disabled` as a literal JSX attribute on <Slot>, which caused
a genuine TypeScript type error ("Property 'disabled' does not exist on
type...") because Slot's declared prop type is generic
HTMLAttributes<HTMLElement>, which doesn't include `disabled` (that's
specific to form elements). Fixed by merging `disabled` into a single
type-asserted spread object instead of a literal attribute — Slot still
forwards it correctly onto whatever the actual child element is at
runtime; only the *literal, individually-checked* JSX attribute was the
problem.

IMPORTANT — read this if your build is still failing with
"Error: supabaseUrl is required.":
This build changes the fix strategy. Instead of wrapping individual pages
in try/catch one at a time (categories, sitemap, etc. — which kept
resurfacing on new pages like Next's internal /_not-found route), all four
Supabase client constructors (browser, server, admin, public, and
middleware) now fall back to a harmless placeholder URL/key if the real
environment variables are missing, instead of throwing synchronously. This
means the BUILD should now succeed regardless of whether your Supabase env
vars are configured in Vercel — but if they're genuinely not set, the
DEPLOYED SITE will still not work correctly at runtime (auth, search,
bookings, everything touching the database will fail). A green build is
not the same as a working app. Please still verify in Vercel → Settings →
Environment Variables that NEXT_PUBLIC_SUPABASE_URL,
NEXT_PUBLIC_SUPABASE_ANON_KEY, and SUPABASE_SERVICE_ROLE_KEY are all set
for the Production environment.
